# Integración con la creación de NPCs

**Código:** `FamilyEngine.adopt(...)` (dos sobrecargas), `NamingEngine.isGeneric`; se dispara desde `LivingReactions.citizenJoined` cuando un NPC llega a una aldea.

## El principio: nunca tocar la creación de NPCs de la Fase 1

El creador de NPCs (`NPCSpawnService`/`NPCManager`, Fase 1) tiene que seguir funcionando exactamente igual con el mundo vivo desactivado. Esta integración no modifica una sola línea de esa canalización: en vez de eso, `LivingReactions.citizenJoined` — que ya se suscribe a la llegada de un ciudadano para darle familia — le pasa también el **tipo** de NPC (`Citizen.npcType()`, p. ej. `"merchant"`) a `FamilyEngine.adopt`, y es `FamilyEngine` quien decide si ese nombre merece ser sustituido.

## Nombre genérico vs. nombre elegido

```java
public static boolean isGeneric(String rawName, String npcType) {
    if (rawName == null || npcType == null || npcType.isBlank()) return false;
    String n = rawName.trim();
    if (n.contains(" ")) return false;                 // dos palabras: alguien lo eligió
    if (n.equalsIgnoreCase(npcType)) return true;       // "Merchant"
    return n.matches(Pattern.quote(npcType) + "_\\d+"); // "Merchant_3" (el sufijo que añade NPCManager.uniqueName al chocar)
}
```

Un nombre de una sola palabra que coincide con el tipo de NPC (con o sin el sufijo numérico que `NPCManager` añade en una colisión) se trata como una etiqueta de repuesto, nunca como un nombre real. Cualquier otra cosa — incluida una sola palabra que no coincida con el tipo, como "Kenji" — se trata como un nombre que alguien eligió y **jamás se toca**.

En `FamilyEngine.adopt(npc, name, ..., npcType)`: si `isGeneric(name, npcType)` es verdadero, la persona nace con un `NameRecord` vacío y recibe un nombre de pila real de la cultura de su familia (`NamingEngine.givenName(...)`); si no, el nombre existente se conserva tal cual (`NamingEngine.parse(name)`, dos palabras se separan en nombre y apellido, una se queda como nombre de pila).

## Un nombre nunca se regenera después

`adopt` solo asigna nombre la primera vez que ve a ese NPC (`Person existing = people.get(npc); if (existing != null) return existing;` corta el paso antes de tocar el nombre). Una vez asignado —genérico sustituido o no—, el nombre de una persona no vuelve a recalcularse en ningún punto del ciclo de vida.

## Un fallo real que esta extensión encontró y corrigió

Al escribir esta integración se descubrió que `LivingReactions.citizenJoined` llamaba a la sobrecarga de **7 argumentos** de `adopt` (sin `npcType`), que internamente pasa `npcType = ""` — y `isGeneric` devuelve `false` en cuanto `npcType` está vacío. Es decir: **la sustitución de nombres genéricos nunca se disparaba en el juego real**, aunque todo el código y las pruebas unitarias de `isGeneric`/`adopt` fueran correctos por su cuenta. Se corrigió cambiando esa llamada a la sobrecarga de 8 argumentos, pasando `c.npcType()`. Sin este cambio, la integración con el creador de NPCs habría quedado escrita pero desconectada — la especificación pide explícitamente que un NPC con un nombre asignado por el sistema reciba uno real, así que el hueco no era aceptable.

## Herencia de apellido dentro de una familia existente

Cuando el NPC que llega ya encaja como pareja, hermano o descendiente de alguien con familia (mismo mecanismo de `HOUSEHOLD_ENGINE.md`), su apellido **nunca se genera por su cuenta**: hereda el de la familia a la que se une (`familyHere = nr.family().isEmpty() ? f.name() : nr.family()`), y su nombre de pila (si hacía falta uno) se genera con la cultura de esa familia (`NameCulture.parse(f.cultureId())`), no con una tirada independiente.
